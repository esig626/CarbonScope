# Declarative stationary hypothesis-testing workflow

The public workflow turns one common SBML/FBC model, explicit H0/H1 flux restrictions and native isotope experiment files into complete feasible state families, stationary genuine-count observation laws and finite composite-testing results. It evaluates the testing performance of a declared experimental design; it does not require observed data or perform generic composite p-value calculation or test inversion.

The workflow calls the existing validated native modelling, sampling, EMU, observation and finite-testing layers. It does not change their numerical contracts. H0 is always P0/null and H1 is always P1/alternative. Type I is the worst represented null probability of deciding H1; Type II is the worst represented alternative probability of deciding H0.

## Complete minimal example: files to report

Run these commands from the repository root:

```bash
python -m pip install '.[testing]'
fluxemu test-hypotheses \
  --specification tests/fixtures/hypothesis_workflow/workflow.yaml \
  --output results/hypothesis_workflow
```

The committed acceptance fixture contains all required inputs:

| File | Scientific role |
| --- | --- |
| [model.xml](../tests/fixtures/hypothesis_workflow/model.xml) | Real SBML Level 3 FBC fixture with canonical reaction order `HX_U`, `HX_L`, `SINK`; two six-carbon glucose feeds enter a G6P pool and the sink is fixed at 10. |
| [experiment.yaml](../tests/fixtures/hypothesis_workflow/experiment.yaml) | Explicit authoritative hexokinase mappings, unlabelled and fully labelled tracer feeds, and the six-carbon `pool-mid` target. |
| [workflow.yaml](../tests/fixtures/hypothesis_workflow/workflow.yaml) | H0/H1 reaction restrictions, finite state generation, genuine-count observation design and testing settings. |

The workflow specification is:

```yaml
schema_version: 1
model: model.xml
experiments:
  - experiment_id: mixed-glucose
    specification: experiment.yaml
    counts:
      - {target_id: pool-mid, replicate_id: counts-1, total_count: 2}
hypotheses:
  H0:
    description: Predominantly unlabelled glucose input
    reaction_bounds:
      - {reaction_id: HX_U, lower_bound: 7.0, upper_bound: 8.0}
    state_generation:
      method: hit_and_run
      count: 2
      seed: 23
      burn_in: 8
      thinning: 2
      max_direction_attempts: 100
  H1:
    description: Predominantly fully labelled glucose input
    reaction_bounds:
      - {reaction_id: HX_U, lower_bound: 2.0, upper_bound: 3.0}
    state_generation:
      method: hit_and_run
      count: 2
      seed: 24
      burn_in: 8
      thinning: 2
      max_direction_attempts: 100
observations:
  semantics: genuine_counts
  independent_blocks: false
testing:
  epsilon: 0.05
  procedures:
    - composite_converse
    - exact_minimax
    - candidate_score
    - analytical_score_bound
    - deterministic_score_error
    - calibrated_score_error
  converse_orders: [2.0]
  score_orders: [0.5]
  max_outcomes: 1000
```

Paths inside this YAML resolve relative to the specification file. Command-line `--model` and `--output` paths resolve from the working directory. The `--model` option can override the YAML's physical model path. This permits the same declared scientific design to be run against an explicitly selected model; the actual loaded model is fingerprinted.

H0 constrains `HX_U` to `[7,8]`, and H1 constrains it to `[2,3]`. The physical model forces `HX_U + HX_L = 10`; neither flux is sampled independently. Each hypothesis is represented by two complete jointly feasible states generated in deterministic order from its declared seed. Stationary EMU predicts a seven-class MID in the order M+0 through M+6. M+1 through M+5 are exact structural zeros. The declared count total is two, so complete enumeration contains 28 count vectors, including zero-probability outcomes. Final observation probabilities are generated by the native model, not supplied by the fixture.

The command writes:

- `results/hypothesis_workflow/report.json`: structured specification, scientific identities, finite states and laws, results, numerical checks and refusal reasons;
- `results/hypothesis_workflow/summary.txt`: the hypotheses, represented family sizes, observation design, evaluated/refused quantities and interpretation limits.

For the committed fixture, a validated run gives these approximate values:

| Quantity | Value |
| --- | ---: |
| Composite converse, order 2 | 0.572530287383 |
| Unrestricted represented finite minimax Type-II error | 0.696682993429 |
| Candidate Rényi divergence, order 0.5 | 0.424578437093; uniform moments verified |
| Analytical projected exponential bound | 13.0809089664 |
| Separate minimax upper bound, using the constant-randomised guarantee | 0.95 |
| Deterministic analytical-score achieved Type-II error | 1, with Type I 0 |
| Calibrated score-family achieved Type-II error | 0.696682993429, with Type I 0.05 |

The raw analytical exponential bound exceeds one and is uninformative here; it is retained as its own mathematical quantity. The calibrated score matches the numerical minimax value for this fixture, while the deterministic analytical threshold does not. This equality is an accepted finite-problem result, not a general least-favourable-pair or minimax claim.

The fixture is compact software acceptance infrastructure. It does not constitute the full biological demonstration planned under issue #24.

## V1 specification contract

The workflow YAML extends the existing native experiment conventions through explicit file references. An experiment file still defines isotope mapping and prediction; it does not acquire hidden hypothesis or count semantics. See [EXPERIMENT_FORMAT.md](EXPERIMENT_FORMAT.md).

Unknown fields and duplicate YAML keys are rejected. Native experiment files loaded through this workflow also undergo strict schema/type checks. Identifiers and correction policies must be strings; use `correction: 'no'` rather than YAML's unquoted boolean `no` when declaring the currently supported correction policy.

### Common model and experiments

`schema_version` is the integer `1`. `model` supplies the SBML/FBC path unless the caller supplies a model override. `experiments` is an ordered nonempty list with unique `experiment_id` values. Every entry names a native `specification` file and an ordered nonempty `counts` list. All experiments must share the same canonical isotope model and authoritative mappings, while tracer and target declarations may differ.

Each count entry references a target from that experiment and declares `replicate_id` and `total_count`. The native mass-class space is retained in full. Experiment order, target/replicate block order and mass-class order are preserved; duplicate block identities are invalid. Count totals are explicit positive integers in `1..2^63-1`, with booleans and floating-point counts rejected. No count total or effective sample size is inferred from MID fractions, percentages, peak areas, arbitrary intensities or corrected data.

`observations.semantics` must be `genuine_counts`. `independent_blocks` is a literal boolean, and multiple blocks require explicit `true`. One count block may use `false`, as in the example. This declaration concerns observation blocks, not independence of sampled flux states. A shared flux state, separate targets or distinct replicate IDs cannot establish independence by themselves.

### H0/H1 reaction constraints

`hypotheses` declares H0 and H1 separately. Each has a nonempty description, an explicit `reaction_bounds` list and `state_generation` settings. An empty `reaction_bounds: []` explicitly selects the common model as a baseline. A reaction restriction names a canonical `reaction_id` and supplies at least one finite `lower_bound` or `upper_bound`. Repeated or unknown reaction IDs, malformed intervals and booleans in numeric fields are invalid. Omit an unspecified bound; a declared `null` endpoint is invalid.

Bounds restrict the common physical model by intersection; they cannot widen its feasible region. Unmentioned reaction bounds remain those of the common model. Equal lower and upper bounds fix a reaction. An explicit zero interval excludes a reaction's flux where consistent with the common model. These are numerical flux statements, without automatic pathway or mechanism interpretation.

Both constrained steady-state regions must be feasible and numerically distinguishable. They may overlap. Native audited FVA must supply an endpoint from one region that violates the opposing region's bounds by more than the native bound tolerance `1e-7`. This tests the complete regions defined by shared balance constraints and different bound intervals; comparing the declared intervals alone would not detect redundant restrictions. Regions lacking such a witness are rejected as identical or numerically indistinguishable. Renaming hypotheses, changing descriptions or changing seeds cannot turn the same region into distinct hypotheses. No hypotheses are inferred from FVA ranges, sample clusters or observed data.

V1 samples the complete region defined by physical steady-state balance and the intersected bounds. It adds no objective-retention constraint. The native experiment's `fva_fraction_of_optimum` is validated but remains a forward-analysis setting; it is not reused to define H0 or H1. Arbitrary coupled inequalities, relaxed physical bounds and inferred biological constraints are outside V1.

### Finite state generation

The supported method is `hit_and_run`, using the native reduced affine feasible geometry. Each hypothesis supplies an explicit `method`, positive integer `count` and nonnegative integer `seed`. `burn_in` is a nonnegative integer, while `thinning` and `max_direction_attempts` are positive integers. Their defaults are 100, 10 and 100 respectively; all effective settings appear in the report.

Every returned state is a complete vector in canonical reaction order and is checked against its hypothesis's constrained region. FVA extrema are geometry diagnostics; they are never assembled into a flux vector or independently sampled. State IDs, constraints, sampling settings, requested/actual family sizes and ordered state fingerprints are retained as provenance.

The generated list defines the **represented finite class** passed to the composite engine. A finite chain is not a guarantee of convergence, independent samples, adequate mixing or coverage of the continuous feasible region. Frequencies, state IDs and flux coordinates do not become priors, weights or decision-statistic inputs.

### Testing settings and result labels

`testing.epsilon` is the Type-I budget, strictly between zero and one. `procedures` is an explicit nonempty list of supported names. `converse_orders` supplies finite real orders greater than one for the composite converse. `score_orders` supplies finite real orders strictly between zero and one for score procedures. Applicable order lists must be explicitly supplied; duplicate procedures/orders and unused nonempty order lists are rejected. Orders are evaluated as declared; there is no silent grid search or claim of a continuous-order optimum. `max_outcomes` is a positive integer enumeration cap, defaulting to 100000. It is never increased automatically.

| Procedure | Result meaning | Enumeration and verification |
| --- | --- | --- |
| `composite_converse` | Order-specific lower bound on represented finite minimax Type-II error. | Full product-law divergence; no joint count-space enumeration. |
| `exact_minimax` | Unrestricted randomised minimax value for the represented finite classes. | Complete declared joint count space and numerically validated LP; may refuse. |
| `candidate_score` | Finite-family Rényi-minimising vertex-pair score with support and uniform-moment diagnostics. | No joint enumeration; a candidate need not verify. |
| `analytical_score_bound` | Verified projected-score analytical Type-II guarantee, separate constant-randomised guarantee and minimax upper bound. | Requires verified uniform moments; no joint enumeration. |
| `deterministic_score_error` | Actual worst-case errors of the verified analytical threshold rule. | Requires its analytical bound and complete joint count-space enumeration. |
| `calibrated_score_error` | Achieved worst-case errors after Type-I calibration within a fixed candidate score family. | Requires a well-defined candidate and complete enumeration; analytical moments may fail. |

A finite-family Rényi minimiser is not automatically a joint convex-class projection or a finite-blocklength least-favourable pair. Calibration is optimal only within its fixed upper-score threshold family and can be strictly worse than unrestricted minimax.

Whenever the applicable quantities are accepted, the workflow checks

```text
composite converse <= represented finite minimax beta* <= achieved Type-II error
```

using a `2e-9` reporting comparison allowance. This allowance does not change solver or certification tolerances. The exact LP retains its original enumeration cap, minimum budget, coefficient-resolution checks and numerical optimality validation. No small positive coefficient is dropped, variable clipped, budget increased or refused calculation replaced with Monte Carlo or an asymptotic approximation. See [COMPOSITE_TESTING.md](COMPOSITE_TESTING.md) for the precise numerical policy.

## Public Python API

```python
from fluxemu import load_hypothesis_testing_spec, run_hypothesis_testing_workflow

specification = load_hypothesis_testing_spec(
    "tests/fixtures/hypothesis_workflow/workflow.yaml"
)
result = run_hypothesis_testing_workflow(
    specification, output_directory="results/hypothesis_workflow"
)
print(result.summary)
print(result.provenance.composite_problem_fingerprint)
for outcome in result.testing_results:
    print(outcome.procedure, outcome.order, outcome.requested, outcome.status)
```

The runner also accepts the specification path directly. Its keyword arguments are `model_path=None` and `output_directory=None`. A model override applies only while loading a file specification. An explicit output argument takes precedence over the YAML output setting; the Python API writes no files if neither is supplied.

To declare persistence in YAML, add:

```yaml
output:
  directory: workflow-results
```

This directory is relative to the workflow YAML. No output path participates in scientific identity. Source file byte digests and the experiment's forward-only FVA fraction remain separately recorded input provenance.

`HypothesisTestingWorkflowResult` is an immutable structured record. It exposes the validated `.specification`, constrained `.null_family` and `.alternative_family`, native `.stationary` result, composite `.problem`, `.null_observation_family`, `.alternative_observation_family`, typed `.testing_results`, `.relationship_checks`, `.refusals`, `.provenance`, `.output_paths` and human-readable `.summary`. Persisted `.output_paths.report` and `.output_paths.summary` identify the two output files.

## Report identity, ordering and reproducibility

`report.json` is deterministic JSON with schema version 1. Its top-level fields include `status`, `identity`, `scientific_specification`, `input_sources`, `hypotheses`, `observations`, `testing`, `results`, `relationship_checks`, `refusals` and `scope`. `status` distinguishes `completed` from `completed_with_refusals`.

`scientific_specification` contains the complete canonical physical/isotope model, ordered experiments with tracer, target and count declarations, H0/H1 specifications, independence and observation semantics, region policy and testing settings. The report therefore retains the scientific inputs themselves alongside their fingerprints. `input_sources` retains source byte digests and forward-only experiment metadata without ephemeral source paths.

Identity includes the canonical model, experiments, workflow specification, H0/H1 hypotheses, finite state families, observation specification/families and composite problem fingerprints. Software/runtime versions, dependency versions, source identity and available commit information are recorded separately from the scientific fingerprints. The runtime source digest covers runtime Python files and packaged authoritative YAML/JSON data. `software_git_dirty_scope` records that Git dirty status concerns `src/fluxemu` and `pyproject.toml`; generated reports outside those locations do not affect it. Ephemeral output paths, timestamps and process IDs do not define scientific identity.

The ordered `hypotheses` list retains H0 before H1, exact declared constraints, state-generation policy and seed, requested/actual family sizes and ordered state IDs/fingerprints. Observation provenance retains experiment/target/replicate identities, genuine totals, explicit independence and exact ordered laws. Testing provenance records roles, budget, supplied orders, requested procedures, enumeration caps and numerical policy.

Every `results` entry identifies `procedure`, `order`, `requested`, `status`, typed result contents or refusal. `status` is `evaluated`, `refused` or `not_requested`. A needed prerequisite may be evaluated even if not explicitly requested; it appears transparently with `requested: false`. For example, requesting deterministic achieved errors requires a candidate and analytical bound. Unrequested, unused procedures are marked `not_requested`.

Bounds, analytical verification, minimax errors, achieved errors and active members remain in their own result objects. Refusal entries include the responsible procedure/order, category, exception type and reason. Mathematical positive or negative infinity is serialised as the strings `"Infinity"` or `"-Infinity"`, keeping the file valid JSON; NaN is not accepted.

Reproducibility requires the same scientific inputs, seeds, software commit, dependency environment and numerical settings. Reruns preserve finite states and report ordering; changing an output directory does not change scientific identity. Different software provenance is recorded even when scientific inputs agree.

## Failure and refusal semantics

The CLI accepts:

```text
fluxemu test-hypotheses --specification WORKFLOW.yaml [--model MODEL.xml] [--output DIRECTORY]
```

It requires an output destination from `--output` or the YAML output setting. The existing `fluxemu run --model ... --experiment ... --output ...` command retains its forward-analysis behavior and outputs.

| Outcome | Python API | CLI |
| --- | --- | --- |
| Valid native construction, requested procedures evaluated | Structured result and optional files. | Exit 0, complete report and summary. |
| Valid native construction, optional procedure explicitly refused | Structured result with refusal reasons; other valid procedures remain available. | Exit 0, report status `completed_with_refusals`. |
| Invalid scientific input or failed construction | Raises a FluxEMU error. | Exit 2 with diagnostic. |
| Failed report persistence | Raises an error. | Exit 2 with diagnostic. |

Invalid construction includes malformed/unknown reaction constraints, infeasible or identical H0/H1 regions, invalid sampling settings, incompatible isotope experiments, undefined stationary EMU evaluation, missing genuine-count declarations, unsupported observation semantics, missing multi-block independence, invalid budgets and malformed or unsupported orders. These inputs are never partially reinterpreted.

Optional statistical refusals include enumeration limits, exact-LP coefficient resolution or certification failures, missing exact-LP dependencies, unrepresentable numerical quantities and failed score verification. A refused analytical certificate remains refused even if direct calibration succeeds. A refusal is a reported limitation, not an estimate of the missing quantity.

## What the result establishes

Accepted outputs evaluate the declared count experiment against its represented finite classes under the stated numerical conditions. A converse establishes an impossibility constraint, not achievability. An achieved procedure supplies finite-class error performance and need not be unrestricted minimax. Numerical equality with minimax is limited to the accepted problem and reported tolerances.

The workflow does not establish uniform guarantees over the complete continuous feasible flux families, identify a true flux or mechanism, or declare biological compatibility from observed data. It does not implement realistic non-count LC-MS/GC-MS laws, new natural-abundance correction machinery, generic composite p-values, compatibility/test inversion, Bayesian nuisance integration, transient inverse MFA or composite testing, experiment-design optimisation, a GUI or the full biological showcase. Issues #24–#28 remain separate work. See [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md).
